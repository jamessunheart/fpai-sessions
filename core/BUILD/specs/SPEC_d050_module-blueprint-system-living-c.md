## Build
Specs are written once and archived. After a build merges, there is no living document that says: this is how this module works now, this is the standard it is held to, this is how it has evolved. Result: every future build starts from partial context. This build creates the Blueprint system — one living document per module, updated after every build, correction, and council review. Blueprints are what make FPOS assemble clearly: each module has a contract, the contract sharpens over time, and every build is written against a defined standard, not a one-time spec.

## Identity

  - Owner: which file/service is authoritative

  - Decision: dNNN (which build created it)

## What it does
  One paragraph. Plain English. What problem it solves, for whom.

## How it works
  - Input: what triggers it / what it receives
  - Process: what it does step by step (not prescriptive — describe actual behavior)
  - Output: what it produces / where results go
  - Side effects: what else changes when it runs

## Quality standard
  What 'excellent' looks like for this module. Measurable where possible.
  Example: 'Onboarding completion rate > 60%. Passport created within first session.'

## Current behavior (verified)
  What is confirmed live and tested. Dated. Updated by smoke tests + ops_ledger.
  Different from 'what it should do' — this is what it actually does.

## Known gaps
  What it cannot do yet. Where it fails or degrades. Source: corrections, council, smoke tests.

## Integration map

## Improvement history
  Dated log: what changed and why. Most recent first.
  Format: YYYY-MM-DD | dNNN | what changed | why it mattered

## Test coverage
  Which smoke tests cover this module. What is NOT tested yet.

## New file: curator/blueprints/manager.py

Function: get_blueprint(module_name: str) -> str
  Loads docs/blueprints/{module_name}.md
  Returns full content. Empty string if not found.

Function: update_blueprint_after_build(decision_id: str, branch: str) -> None
  Called after auto-merge in server_build_loop.sh
  Determines which module was affected (reads REGISTRY.json or diff path)
  Loads current blueprint for that module
  Runs claude -p (--effort high):
    'Update this module blueprint to reflect what this build added or changed.     Update sections: Current behavior, Known gaps, Improvement history.     Do NOT change: What it does, Quality standard (unless explicitly improved).     Be specific and dated. Blueprint: {current} | Build diff summary: {diff_summary} |     Build spec: {spec}. Output the FULL updated blueprint.'
  Writes updated blueprint back to docs/blueprints/{module_name}.md
  Commits: 'docs(blueprint): update {module_name} after {decision_id}'

Function: update_blueprint_after_correction(module_name: str, correction: str) -> None
  Called by corrections.py when a correction is captured
  Appends to Known gaps: 'YYYY-MM-DD: {correction}'
  Does NOT regenerate full blueprint — just appends (fast, cheap)

Function: sharpen_quality_standard(module_name: str) -> None
  Called by council after a successful round of improvements
  Runs claude -p: 'Given current behavior and recent improvements,   propose a higher quality standard for this module. One paragraph.   Must be measurable. Must be achievable in next 3 builds.'
  Presents to James via TG: 'Quality standard proposed for {module}. Reply yes to adopt.'

Known gaps accumulate from real James corrections, not just planned gaps.

## Blueprint evolution loop (the compounding mechanism)
1. Blueprint defines current standard
2. Council reads blueprint → proposes build to close a known gap or raise the standard
3. Codex reads blueprint → builds against the standard, not from scratch
4. Review reads blueprint → checks if build met the standard
5. Merge updates blueprint → standard raised, gap closed
6. Correction updates blueprint → real gap added
7. Next council sees sharper blueprint → proposes sharper improvement
This is the compounding loop. Each cycle, the standard rises.
